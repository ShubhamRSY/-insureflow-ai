Primer

How a commercial underwriter actually works

Before the code: the job itself. Every stage of the pipeline exists because a human underwriter does that step.

A commercial underwriter works for an insurance company (the carrier). Brokers send them businesses that want insurance. For each one, the underwriter decides whether to insure it, on what terms, and at what price, and must be able to defend that decision to their manager, the reinsurers and the state regulator.

The four questions behind every file

Do we want it?Is this kind of business, in this place, at this size, something we write? (appetite)
What could go wrong?Fire, wind, flood, theft. How likely, and how big could one loss be? (COPE, catastrophe exposure)
How has it gone before?Past claims: how many, how large, still open, any lawsuits? (loss history)
What makes it worth it?Price, deductible, limits and conditions that make the risk acceptable. (pricing, terms)

The words for the outcome

  • Accept: quote at the indicated price.
  • Conditional accept: quote, but "subject to" conditions (for example, "subject to a sprinkler retrofit plan within 90 days"). These conditions are called subjectivities.
  • Refer: outside this underwriter's authority or comfort; a more senior person decides.
  • Decline: the carrier will not write it.

Why underwriters are cautious

Premium arrives once a year; one bad fire can cost 50 to 100 times that premium. An underwriter is judged on the loss ratio of their book: claims paid divided by premium collected. Most carriers need it well under 65% to make money after expenses. Every rule in this pipeline exists to keep bad risks out, or to charge enough for them.

Case · Northwind

A real underwriter would read Northwind like this. Trucking company, so not a preferred class (appetite: maybe). A $28.5M warehouse, part of it unsprinklered with combustible packaging (what could go wrong: a large fire). 14 claims in five years, $1.89M incurred, one lawsuit (how it has gone: poorly). And the SOV claims full sprinklers while the inspection disagrees (trust: low). The verdict is to refer, require sprinklers in the cross-dock, raise the deductible, and price up. The pipeline reached nearly the same answer.

Lesson 00

The big picture

What goes in, what comes out, who decides, and where the 7.8 seconds go.

The problem

A broker sends a stack of documents about a business's buildings. An underwriter must read all of it, cross-check it, judge the risk and price it. By hand this takes hours per file, and most of that time is reading and re-typing.

The idea

Let software do the reading, checking and arithmetic, and hand the underwriter a finished memo and quote to judge. The person still makes the decision; they just stop doing clerical work.

Lesson 02

Life of a request

How a slow job survives inside a web API.

The problem

The pipeline takes seconds to minutes. A browser request that waits that long times out, and if the server restarts mid-run, the work is lost.

The idea

Answer immediately with a ticket (a job id). Do the work in a separate worker, and let the client watch progress by polling or by a live stream.

  1. The API checks the caller's role (viewer or higher) and a rate limit of 10 runs per minute.
  2. It writes status: processing to the job store, scoped to the caller's organisation.
  3. It queues the job to Celery. If Celery is off or the queue fails, it runs the same function in-process with FastAPI BackgroundTasks, so the client never notices.
  4. The worker updates progress after every stage; the dashboard reads it over a server-sent-events stream.
  5. Redis drops jobs after about a week. A later request rebuilds the job from the encrypted audit archive.

Lesson 03

Reading the documents

The step that takes the longest, and the one where Northwind went wrong.

The problem

Files arrive with random names in many formats. Before anything can be extracted, the system has to know what each file is, because a loss run and an inspection report are parsed by completely different code.

The idea

Classify each file by keywords, then send it to the parser for that type. Keywords are fast, free and predictable. Their weakness is that a word can mean two things.

How the code does it

  1. Guard. Virus scan (ClamAV, fails closed if configured but down), macro and active-content checks, locked PDFs, and limits against zip bombs: 200 files, 500 MB unpacked, 3 levels deep.
  2. Classify. InsuranceDocumentClassifier.classify() lowercases the filename plus the first 8,000 characters and walks a long list of keyword rules from top to bottom. The first rule that matches wins.
  3. Parse. ACORD XML goes to a schema parser and becomes structured data. Other types go to their own parsers. Scanned PDFs go through OCR first.
  4. Check the package. Missing ACORD 140, SOV or loss run is a CRITICAL finding. Missing roof age or protection class is MODERATE. These are findings, not stops: the run continues.
Case · Northwind

Four files went in. The ACORD became structured data. The SOV was classified correctly. The loss run and the inspection report were both classified as retirement_account_statement, a life-insurance document, because both describe a truck rollover.

As a result the package checklist found 3 of 18 property documents (17%), and the system reported "Missing required document: Loss run reports" as CRITICAL. A real underwriter would see 14 claims and $1.89M incurred, including an open auto liability claim.

Watch out

First-match keyword classifiers break on ordinary words. Two safer patterns: check the current line of business first (a commercial property package should not contain retirement statements), and score all rules then take the best, instead of the first hit. This is exercise 1 in lesson 13.

Lesson 03b

Images: scans, handwriting and property photos

Two very different kinds of image arrive in a package, and each takes its own path.

The problem

Many documents arrive as pictures of paper: a scanned loss run, a phone photo of a signed form, a handwritten note. Separately, brokers attach photos of the building itself. Text has to be recovered from the first kind; risk has to be judged from the second.

The idea

For documents, try the cheapest way to get text first and climb a ladder of stronger engines only when needed. For photos, measure picture quality first, then look for hazards and damage, and never trust a photo that looks edited.

Lane A: how the router picks a reader

If the file…RouteRead by

  • Rotation: Tesseract first asks the page which way is up (OSD) and rotates it, so sideways scans still read.
  • Handwriting: with USE_HTR=1, a detector looks for uneven stroke widths. Above 0.4 confidence the page goes to Microsoft's TrOCR model, and its output is accepted at 0.3 confidence or more.
  • Page positions: pdfplumber records a box for every line, so a finding can later point at page 3, line 12. This is what lets the citation gate work.
  • Big files: uploads over the auto-processing limit are kept but not OCR'd, and are flagged for manual review instead of risking an out-of-memory crash.
  • Bad files: the document quality gate subtracts penalties from 1.0. Empty is −0.5, OCR failure −0.3, unusually short −0.15. Under 0.3 is a reject, which blocks straight-through processing.

Lane B: the photo quality score

After quality, a vision model (if configured) or a local heuristic looks for roof wear, exposed wiring, stored combustibles and water damage. The forensics check flags edit-software tags and JPEG re-compression hotspots, and asks for the original camera files. The property's visual risk is its worst photo, never the average, so one bad roof photo cannot be diluted by ten nice ones.

Case · Northwind

Northwind's four files were text, so neither ladder was needed: regex found 120–350% of expected fields. Had the broker attached roof photos, they would have hit the bug above: the stage would say "0 photos · low risk" and nobody would know the photos were never looked at.

Watch out

A stage that silently does nothing looks exactly like a stage that found nothing. The fix is one line (pass image_data as decoded bytes), and the lesson is general: assert that "analyzed" equals "received".

Lesson 04

Rules before AI: the Zero-Token router

How the system decides, task by task, whether a language model is needed at all.

The problem

LLM calls cost money, take seconds, can make things up, and give different answers on different runs. An underwriting file needs to be cheap, fast, and reproducible for auditors.

The idea

Before each task, ask: can rules do this well enough? Only if not, and only if a model is allowed, use one. Log every decision with the tokens it saved or spent.

Case · Northwind

The router logged 5 decisions. All three documents were read by rules, with regex finding 120%, 350% and 300% of the expected fields. Reconciliation found 6 conflicts and wanted the LLM, but none was available, so it was escalated to a human. The memo was built from a template. Tokens used by the router's tasks: 0.

Lesson 05

Agents and the ReAct loop

What "agent" means here, how they work together, and what happens when the AI is unavailable.

The problem

Judging a risk needs several kinds of expertise: claims history, compliance, fraud, physical risk. One giant prompt would be slow, hard to test and hard to explain.

The idea

Split the work into specialist agents, each a Python class that returns findings, a 0–1 risk score and a recommendation. Run them in parallel, then let a final agent combine them.

Inside one agent: the ReAct loop

Four of the five are ReAct agents (reason + act). Instead of answering in one shot, the model works like an analyst with a calculator:

  1. Think. The model reads the task and decides what it needs, for example "I need the claim frequency".
  2. Act. It names one of 18 tools, such as compute_claim_frequency. Python runs the tool, so all arithmetic is exact.
  3. Observe. The tool's result is added to the conversation. Back to step 1, at most 10 times.
  4. Answer. When it has enough, it returns final_answer with its findings.

If anything fails (no key, a 401, a timeout), the agent throws away partial LLM output and runs its rule-based _analyze() instead, which returns the same shape of result. After 3 failures in a row a circuit breaker opens for 60 seconds and agents skip the LLM entirely.

Case · Northwind

The .env OpenAI key was rejected (HTTP 401). Each ReAct agent spent about 1.5 s on the failed call, then fell back to rules. The memo was still produced, with score 0.65 and REFER, because the rule paths are complete on their own. The only visible trace is the "1 error" on each agent's summary.

Watch out

Silent fallback is good for availability and bad for awareness. Northwind looks normal unless you read the agent errors. Check memo.agent_results[*].errors after a run, and rotate the key in .env.

Lesson 06

Trusting the facts

How the system notices when documents disagree, and refuses to state anything it cannot point to.

The problem

The same fact appears in several documents, often with different values. Brokers make typos, applications are optimistic, inspections find surprises. A memo that silently picks one value hides the most important signal.

The idea

Remember where every value came from (provenance), compare values across documents (reconciliation), and refuse to publish a claim that has no source (citation gate).

Three checks after the memo is written

  1. Citation gate. Every figure in the memo must trace to a source document. Uncited figures become CRITICAL findings. If the gate itself crashes, it adds a CRITICAL finding and forces REFER. This is called failing closed: a broken safety check never turns into a pass.
  2. Confidence floor. A coverage limit, deductible or premium read with under 60% confidence must be confirmed by a person.
  3. Oracles. Outside databases (CLUE and A-PLUS claims history, NCCI, a catastrophe model, credit bureau, public records, OSHA, a rating agency, and the OFAC sanctions list) confirm or contradict what the broker said.
Case · Northwind

Provenance traced 69 fields; 17 were verified by a second source. Reconciliation found 6 conflicts. The citation gate added 4 CRITICAL "unverified figure" findings, for example the SOV's total value, which could not be matched to the application.

Oracles (in mock mode) found prior litigation on CLUE (CRITICAL), an open auto liability claim, a clean A-PLUS property history and an NCCI mod of 1.000. Four lookups failed in mock mode and were recorded as findings, not ignored. OFAC: no match.

Lesson 07

Making the call

How 39 findings become one word, using arithmetic you can check by hand.

The problem

Underwriters must be able to explain every decision to a regulator. A neural-network probability cannot be explained finding by finding.

The idea

Score = the average weight of the findings, plus a small bonus when many pile up. Then apply plain rules in a fixed order. Anyone can redo it on paper.

# each finding contributes: contribution = severity weight × (0.5 + 0.5 × confidence) critical 1.00 · high 0.75 · moderate 0.50 · low 0.20 # the score: score = average contribution + min(0.15, log2(1 + number of moderate-or-worse) ÷ 6 + 0.1 per fraud / moral hazard / selection finding, max 0.3) # findings about failed lookups or the citation gate are left out of the score

Then the rules, in order

  1. 10 or more claims per year → DECLINE, whatever the score.
  2. Any CRITICAL finding → REFER. Most critical findings are missing data, which needs a person, not a decline.
  3. Any HIGH finding, or score ≥ 0.70 → REFER.
  4. Only MODERATE findings → CONDITIONAL ACCEPT, with "SUBJECT TO" conditions.
  5. Otherwise → ACCEPT. A later pass declines anything scoring 0.85 or more.

Lesson 08

Pricing a building

How $28.5M of buildings became a $383,852 premium, one multiplication at a time.

The problem

Carriers must charge the rates they filed with each state, and every adjustment must be justified. A single opaque number is useless to an underwriter who wants to negotiate.

The idea

Start from the filed rate, then apply each adjustment as a visible step. The quote lists every factor so any one can be challenged.

StepWhyChangeRunning total
Filed base$28.5M ÷ 100 × 0.6954 × 2.063 × 0.94 (Illinois)–$384,332
MarketThe market is soft, so rates are 8% lower−$30,747$353,585
Schedule credits"sprinkler" −5% and "alarm" −3%, matched as words in the documents−$28,287$325,299
Property checklistHigher-hazard occupancy, no sprinklers in part, flammable storage, combined fire scenario+$58,554$383,852

How the code does it

  1. Because the product is property_bi, the engine uses the carrier's filed rate for that product (SERFF-IF-PROPERTY_BI-2026A). Without a product id it would use a generic ISO/COPE formula instead.
  2. Every commercial property quote then passes one function that adds state-law notes (valued policy law, named-storm deductibles, wind pools) and checks coinsurance.
  3. Finally the property checklist scores hazards and can add a premium percentage, require mitigation, or refer.
Watch out

Schedule credits are applied when the word appears anywhere in the package. Northwind got the −5% sprinkler credit and, in the same run, a HIGH finding for missing sprinklers. The two steps disagree and the price nets them out. A better rule would read the sprinkler field per location instead of searching for the word.

Lesson 09

RAG: looking up the rulebook

How the system finds the right underwriting guideline, and why property doesn't use it inline.

The problem

A language model doesn't know this carrier's guidelines and will invent plausible ones if asked.

The idea

Retrieve the relevant guideline passages first, augment the prompt with them, then generate an answer that must cite them.

  • What is indexed: underwriting guidelines and appetite rules only. No customer submission is ever embedded.
  • Where vectors live: the first one configured among Chroma, Weaviate, Postgres + pgvector, or memory.
  • Embeddings: intfloat/e5-large-v2 locally or OpenAI text-embedding-3-small; hashed vectors when neither works.
Case · Northwind

No guideline retrieval ran. Inline RAG is wired only for D&O, Trade Credit, E&O and Key Person. Property gets its rules from the appetite table and the coded property checklist. The one embedding call in the run (for "similar past decisions") failed without a valid key and fell back to hashed vectors.

Bug hunt, ranked by impact

0 · Uploaded photos are never analyzed
insurance/pipeline.py:720 passes the raw document dicts (filename, content) to PropertyPhotoAnalyzer, which reads photo["image_data"] (ml/vision/pipeline.py:57). Every photo is skipped. Decode the base64 into image_data and assert analyzed == received.
0b · Appetite and triage run before anything is parsed
On the upload path acord_xml is None when stages 1–2 run, so they score an empty bundle. Re-run appetite after ingest (stage 2b already re-runs triage), or parse the ACORD first.
1 · "Rollover" turns a loss run into a retirement statement
ingestion/insurance/classifier.py:441 matches "rollover" before the loss-run rule at line 522. Write a failing test with the Northwind loss run, then fix it. Options: skip life-only rules when the package is commercial; or require stronger retirement phrases ("401(k) rollover", "IRA rollover"). Rerun the lab: the CRITICAL "missing loss run" should disappear and 14 claims should appear.
2 · Agents ignore use_llm=False
InsurancePipeline(use_llm=False) only affects the extraction agent. SupervisorAgent builds its own LLMClients. Decide whether the flag should reach the supervisor, and make the lab run with zero LLM calls.
3 · The sprinkler credit and the sprinkler finding disagree
rating/leaf_filings.py applies schedule credits when the word appears in the package. Change it to use the structured protection data per location, so a file with an unsprinklered area does not earn the full credit.
4 · The conflict note can name the wrong winner
agents/supervisor.py:280 uses max() on severity strings: max("critical", "low") is "low". Use the severity_map defined a few lines above.
